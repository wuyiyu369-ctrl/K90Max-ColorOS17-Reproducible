# K90 Max ColorOS 17 Stage51 联合审计

日期：2026-11-07
当前设备：`<REDACTED_DEVICE_SERIAL>`
当前系统状态：`sys.boot_completed=1`，SELinux Enforcing
当前交付镜像：`K90Max_ColorOS17_Prague_KEEPDATA_Stage51_NAME_CHARGE_FAN`

## 一、结论

Stage51 能启动，但不能作为下一版的直接构建基线。

主要原因不是单一功能补丁失败，而是 `product`、`odm` 重建时发生了 SELinux 文件标签回归，同时 Stage51 对名称、充电和性能接口的修复没有落到真正生效的分区或完整调用链。

下一版应从 Stage49 干净基线重新构建，保留 Stage49 回滚包，不能继续在 Stage51 的 `product.img`、`odm.img` 上叠加。

## 二、当前镜像完整性

Stage51 `super.img` 实际 SHA-256：

```text
596341C5CBB5C0D04101A5B61D407B53A71C6D2B7EE4E077F5A1B5B75A38F1BA
```

与交付目录 `SHA256SUMS.txt` 一致，说明磁盘上的 Stage51 文件本身没有损坏。

但“哈希一致”只证明文件没有被意外改写，不代表镜像内容正确。

## 三、镜像元数据回归

Stage49 与 Stage51 回读对比：

```text
/product/bin
Stage49: u:object_r:system_file:s0
Stage51: 无 security.selinux 标签

/odm/lib64/libc++_shared.so
Stage49: u:object_r:vendor_file:s0
Stage51: 无 security.selinux 标签
```

当前实机日志对应出现：

```text
tcontext=u:object_r:unlabeled:s0 name="bin" dev="dm-2"
camerahalserver ... libc++_shared.so ... tcontext=u:object_r:unlabeled:s0
```

本次完整日志计数：

```text
unlabeled: 3512
其中 name="bin": 3318
libc++_shared.so: 189
```

直接根因在 Stage51 构建脚本：

1. 人工创建了 `product_upper/bin`，但没有写入 SELinux xattr。
2. ODM 通过 overlayfs 合并后重新生成 EROFS file contexts，只给新增文件设置 override，未保证所有 lower 文件标签原样保留。
3. 构建后的验证只检查新增文件，没有做全树、不跟随符号链接的属主、权限、链接、xattr 对比。

影响范围不只相机，还包括启动脚本、shell 工具、硬件服务、SurfaceFlinger/Launcher 间接调用和大量重复 AVC。

## 四、风扇

当前设置：

```text
cooling_fan_main_switch=1
cooling_fan_mode=2
```

最新复现日志：

```text
K90NativeBridge: fan-applied pkg=com.android.settings result=99
K90NativeBridge: fan-speed-readback pkg=com.android.settings result=2
```

这说明 Stage51 已完成以下软件链路：

```text
ColorOS Settings
→ K90ThermalBridge
→ /data/system/k90fan.request
→ k90_native_bridge
→ target_level=0
→ pwm_duty=99
```

旧 KSU 模块文档已经说明 `real_speed=2` 是恒定哨兵值，不是真实 RPM，不能据此判断风扇没有转。

目前能确认的是“最大 PWM 请求已经写出”。是否真实转动仍需用声音、气流或有效的驱动测速节点确认。下一版需要增加：

- 请求模式、温度、目标 PWM、写入后 PWM 回读；
- mode 0/1/2/3 的明确映射；
- 智能模式温度阈值与游戏/充电场景；
- 满电非游戏停转、满电游戏仍按游戏曲线转动；
- 不再把 `real_speed=2` 展示成真实转速。

## 五、关于本机、蓝牙和热点名称

当前运行值：

```text
ro.product.model=PMB110
ro.product.marketname=PMB110
ro.product.product.model=ossi
device_name=PMB110
revise_device_name=PMB110
```

Stage51 修改了 `/product/etc/build.prop`，但实际覆盖名称的来源是：

```text
trees/pmb_my_manifest/build.prop
```

该文件前部仍有：

```text
ro.vendor.oplus.market.name=PMB110
ro.product.name=PMB110
ro.product.model=PMB110
ro.product.marketname=PMB110
```

文件后面虽然又追加了中文 `ro.vendor.oplus.market.name`，但只读属性已经先被 PMB110 初始化，重复追加不能可靠覆盖。

正确方案：

1. 从 Stage49 的 `my_manifest` 分区重建极小镜像；
2. 原位替换首次出现的用户展示属性，不再追加重复 key；
3. 不修改 vendor/odm 的 `prague` 硬件身份、attestation、fingerprint、bootimage 身份；
4. 由 `K90ThermalBridge` 在 system_server 内执行一次性 Settings 迁移，写入关于本机、蓝牙和热点名称；
5. 不再由 init 服务执行 `settings` 命令。Stage51 的 `k90-user-names` 已运行并停止，但没有写成功。

## 六、充电与 100W 显示

当前服务：

```text
vendor.oplus.hardware.charger.ICharger/default: found
```

说明 Stage51 的兼容服务已启动，但真实数据读取仍被拒绝：

```text
vendor_touch_init_shell → sysfs_usb_supply: denied search
vendor_touch_init_shell → sysfs_ti_battery/cp_master: denied search
vendor_touch_init_shell → vendor.xiaomi.hardware.micharge.IMiCharge/default: denied find
```

日志计数：

```text
sysfs_usb_supply: 1175
sysfs_ti_battery: 121
```

另有重复 service-context：

```text
Multiple same specifications for vendor.oplus.hardware.charger.ICharger/default
```

因此当前兼容服务虽然注册成功，但没有可信协议、最大输入能力和充电泵状态，不能正确给 ColorOS 返回快充类型。

正确方案：

- 给 `vendor_touch_init_shell` 精确开放 USB、TI battery、MiCharge service-manager 和 binder 权限；
- 只保留一处 `ICharger/default` service-context；
- 默认配置移到 `/odm/etc/k90/`，避免 vendor init 跨 product 读取；
- 补齐状态文件原子替换需要的窄范围 rename/unlink/remove_name 权限；
- 分开显示“协议上限 100W”和“当前实时功率”，不能把 17W 实时功率伪造成 100W。

- 前台启动、桌面动画、相机、轻游戏、重游戏、跑分分别映射；
- GPU/GED、DDR、UFS 采用真实接口和可回读状态；
- 保留 Xiaomi 热保护，不常驻锁最高频率。

## 九、NPU 与 ColorOS AI

MTK APU/NPU 服务均在线：

```text
vendor.mediatek.hardware.apuware.aiste.IAisteService/default
vendor.mediatek.hardware.apuware.apusys.INeuronApusys/default
vendor.mediatek.hardware.neuropilot.neuronservice.INeuronService/default
```

但 `com.oplus.aiunit` 日志明确显示：

```text
/odm/lib64/libaiboost.so not found
OAA path not exist
libaiboost_llm.so not found
engine SO load failed
worker29 随后被 AIUnit 主进程 SIGKILL
```

结论：NPU 硬件/MTK 服务存在，ColorOS AI 推理后端未接入。当前问题不是简单提高 NPU 频率。

修复方向：

1. 审计 ACE7/当前 donor 的 `libaiboost.so`、依赖库、模型版本和许可；
2. 不能直接放入单个 so，必须完成依赖、namespace、模型路径、SELinux 和 APU backend 适配；
3. 优先做最小推理 smoke test，成功后再启用 AIUnit 功能；
4. 未接通前禁止让 worker 周期性重试和下载大模型造成耗电。

## 十一、Stage52 推荐顺序

1. 释放 D 盘至少 20 GB。
2. 从 Stage49 干净 `super.img` 开始，不复用 Stage51 的 product/odm。
3. 重建 `my_manifest`，原位修改中文展示名。
4. 把名称一次性迁移加入 system_server 内的 `K90ThermalBridge`。
5. 修复 Stage51 的 product/odm 全树 SELinux 标签生成方式。
6. 修充电 sysfs、MiCharge binder、状态目录和重复 service-context。
7. 补 ColorOS `IPerformance/IUrcc` 到 UniPerf/MiPower/MTK Power 的最小真实翻译层。
8. GPU/DDR/UFS 先完成真实读回，再配置桌面、相机和游戏策略。
9. AIUnit/NPU 单独做最小后端验证，不能与基础启动链一次性混入。
10. 完成离线校验后才刷写：
    - `fsck.erofs`
    - AVB footer 回读
    - UUID/label
    - 全树属主、权限、链接、SELinux xattr diff
    - 所有新增文件明确 file_context
    - 不存在任何 `unlabeled`
    - super 修改区间与未修改区间比较
    - 敏感分区清单检查
11. 保留 Stage49，保数据刷 Stage52，完成两次启动、风扇、充电、名称、桌面、相机和性能回读验证。
