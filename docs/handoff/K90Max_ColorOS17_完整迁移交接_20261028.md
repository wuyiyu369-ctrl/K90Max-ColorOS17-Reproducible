## 4. 已经修复或确认有效的项目

### 4.1 可开机的安全 framework 修改方式

- Stage13C 不再完整反编译/重编 `framework.jar` 的全部 DEX。
- 使用 `PatchDexInPlace.java` 对原始 `classes2.dex` 做等长指令字节修改，再用 `ReplaceZipEntry.java` 替换原 ZIP 条目。
- 修改前后公开 API 数量均为 `541427`，`MISSING=0`、`ADDED=0`。
- 该方法已实机开机验证，避免了旧版重编 DEX 导致的 bootloop。
- 关键文件：`stage13\PatchDexInPlace.java`、`DexInstructionDump.java`、`ReplaceZipEntry.java`、`build_stage13c_system.sh`。

### 4.2 通信身份分层

ColorOS 的 `/my_manifest/build.prop` 曾覆盖 vendor/odm 身份，导致基带按 PMB110/OP64D7L1 选择错误 NV。正确方案是只删除 my_manifest 中以下底层覆盖：

- `ro.product.vendor.{brand,device,model,name,manufacturer}`
- `ro.product.odm.{brand,device,model,name,manufacturer}`
- `ro.vendor.build.fingerprint`
- `ro.odm.build.fingerprint`

让 vendor/odm 自己的 `Redmi/prague/2604FRK1EC` 生效。不要删除 `ro.vendor.oplus.*`、`ro.oplus.*`、应用层身份或 OTA 元数据。

### 4.3 状态栏信号等级

- 根因：ColorOS 调 `SignalStrength.getSignalStrengthLevel()`，但本机没有组件调用 `setOEMLevel()`，结果始终 `[0,0]`。
- 修法：framework 中返回真实 `getLevel()`，两个槽位均取真实 framework 等级，不伪造满格。
- 现场证据：`isInService=true level=4`，底层 NR RSRP 也为有效值。
- 双卡“合并/独立”仍需用双实体 SIM 做最终回归。

### 4.4 指纹底层类型（仅部分完成）

- 已内置 `persist.vendor.fingerprint.sensor_type=ultrasonic`。
- 已内置位置参数 `iconlocation=690`、`iconsize=196`。
- `dumpsys fingerprint` 能看到 sensorId 5、HAL deaths=0、`mSensorType=2`，并出现过真实 acquire/accept。
- 这只能证明 HAL 和传感器链路可工作；锁屏图标、SystemUI UDFPS 路由和录入界面仍未原生完成。

### 4.5 充电真实状态与误报修复

- `oplus-services.jar` 中增加 K90 兼容桥，从标准 `BATTERY_CHANGED` 和 `BatteryManager` 取真实电压/电流。
- ColorOS 附加电池广播原先因为没有 OPLUS charger HAL，把 `notifycode` 发成 `-1`。SystemUI 对它做位掩码判断时把所有错误位都视为 1，从而把正在充电判成异常/未充电。
- Stage14 只把负数“不可用哨兵”规范为 0，真实非负错误码仍保留；`chargertechnology` 缺失时保持中性 0，不冒充 VOOC/SuperVOOC。
- 实机日志已出现 `batteryCharging=true`、`ChargeStateModel charging=true`。
- `sys.batterylow.hidetips=true` 用于抑制已确认由缺失 OPLUS HAL 造成的“充电电压过高”假通知。
- 尚未完成真正的快充协议类型和输入端瓦数；目前 battery-side 计算值不能当充电器协商功率。

## 5. 当前没有完成的项目（按优先级）

### 5.1 CPU 底层性能调度

已确认根因：

- MTK PowerHAL 服务正常存在并尝试写 `/proc/powerhal_cpu_ctrl/perfserv_freq`。
- 节点默认 `0444/0660 system:system`，PowerHAL 日志持续出现 `Could not open`、`error 13`、`retry_Cpufreq`。
- 手动 root `chmod 0666` 后错误立即归零，频率建议能够写入，证明不是 CPU、驱动或硬件性能不足。
- Stage14 init rc 虽写了 `chmod 0666`，但 SELinux 拒绝 `init` 对 `proc_powerhal_cpu_ctrl:file setattr`，重启后仍为 `0660`。

下一步正确修法：

1. 在 vendor sepolicy 中为实际执行域增加最小规则，优先只允许 `init` 或专用守护域对 `proc_powerhal_cpu_ctrl:file setattr/open/write`；不要全局 permissive。
2. 更好的方案是建立专用 oneshot native service，赋予单独 SELinux 域，仅负责权限设置和必要写入。
3. 验证重启后节点为可写；连续 10 秒日志中 `Could not open` 和 `retry_Cpufreq` 都为 0。
4. 不锁定最高频率、不禁用 `mi_thermal_interface`、不绕过温控。

现场拒绝证据：

```text
avc: denied { setattr } scontext=u:r:init:s0
tcontext=u:object_r:proc_powerhal_cpu_ctrl:s0 tclass=file
```

### 5.2 充电剩余部分

- 状态判定已通，但 `ChargerTechnology`、真实适配器协议、输入端瓦数仍缺 OPLUS charger HAL。
- 不应把电池端 `voltage × current` 冒充充电器输入瓦数。
- 应从 Xiaomi `micharge-hal`/power_supply 节点确认：适配器类型、总线电压、总线电流、PPS/私有快充状态，再由小型兼容服务生成 ColorOS 需要的广播字段。
- 必须测试插入、拔出、息屏、重启、低电量、高温五种情况，尤其检查拔线延迟和绿色状态是否残留。

### 5.3 指纹 UI 与录入

- 底层传感器类型已识别，但锁屏 FOD 图标仍不显示。
- ColorOS SystemUI 还要求 `KeyguardFeatureOption.isSupportUdfps()`、`isSupportUltrasonicFps()`、正确 AIDL pointer 路由和 FOD overlay。
- `pixel_pitch=-1` 会使图标半径计算失败；运行期 RRO 被 idmap2 以“overlay must be preinstalled”拒绝。
- 原生方案应在镜像内预置签名/目标正确的 overlay，或在 SystemUI 等长修改决策点；不要直接重签 SystemUI。
- 旧 LSP 有可参考实现：`FodUiHooks.java`、`FingerprintTypeHooks.java`、`AidlFodBridge.java`、`UltrasonicGeometryHooks.java`、`UltrasonicEnrollHooks.java`。

### 5.4 人脸

- 旧人脸可解锁，但删除后重新录入可能失败或进度异常。
- `miface` 能收到相机帧，算法返回 code 11；日志还见到 TEEC 和 `/proc/perfmgr/perf_ioctl` SELinux 拒绝。
- 旧 LSP 只补 UI 里程碑，不伪造最终成功；原生修复要确认 `mifaced/libmiface.so` 回调、TEE 能力和 SystemUI UI 三层。

### 5.5 AOD/息屏显示

- 快速消失与 SystemUI `doze-stuck-watchdog`、虚拟距离传感器方向和设备能力声明有关。
- LSP `AodHooks.java` 曾只在持续显示模式抑制 hide alarm，并针对 Prague 反转 AOD proximity 回调。
- K90 面板不应被宣传为不存在的 1Hz LTPO/LTPS；不能通过属性伪造硬件档位。

### 5.6 小米相机

- 已遇到：8K 崩溃、60fps 档缺失、录像按钮不可用、第三方调用黑屏/不返回、照片保存延迟、MIVI 重算法超时、无 5× 硬件却显示 5×。
- 已确认过 `Canvas.saveUnclippedLayer(...)` 兼容问题；修复后可以打开，但不是完整相机适配。
- 根因跨 FeatureParser、MIVI 后端、gralloc、MTK Camera HAL 和图库返回 URI。不要只伪装机型。

### 5.7 电源键延迟

- 探针确认内核 evdev 交付 KEY_POWER 约 2–30ms，慢在 Android framework 路径，常见恒定约 5 秒。
- 旧 `pkgrd` 用 `EVIOCGRAB` 抢按键再注入 WAKEUP，能降到 70–150ms，但会破坏音量键、长按、截屏组合键，不适合直接内置。
- 正确原生方案应修 framework 的 PowerKey/PhoneWindowManager 延迟条件，不再独占整个 event0。

### 5.8 NFC 钱包、eID、查找手机和 Key 状态

- 普通 NFC 已在 A17 基线恢复过，但 OPPO 钱包/eID/查找手机依赖 OPPO TEE TA、RPMB 私钥、cryptoeng 和 StrongBox。
- Prague 是小米 MiTEE/NXP StrongBox，不能复制或模拟 OPPO 私钥；假装成功只会让 UI 变绿，服务端仍失败。
- `DEFAULT_ROUTE=0xC0` 指向不存在的 ESE，Prague 实际只有 DH handle `0x400`。曾尝试改路由为 DH 后 HAL open 崩溃；中途 stop/start NFC HAL 还会破坏初始化时序。
- 不要再“模拟安全芯片”或伪造 Key 状态。

### 5.9 O-Haptics、MiSound/Bose、刷新率和独显

- O-Haptics feature 声明本身不等于 HE 包络可用；需要在 `oplus-services.jar` 映射到小米 vibrator HAL。
- MiSound/Bose 控制与 DSP 配置在 vendor，不能只复制 XML。需核对 audio_effects、库 ABI、DSP UUID 和 selinux。
- 165Hz 是物理档，但 ColorOS 缺 `IDisplayPanelFeature`；90Hz 可做应用 override，不能伪造不存在的面板档位。
- 小米独显、风驰引擎和 OPPO GPU 魔改不能仅靠属性启用，必须匹配驱动、firmware、HAL 和 framework 消费者。

## 6. 失败历史与根因（必须阅读）

### 6.1 framework 完整重编导致无震动/无限重启

旧方案用 smali/dexlib2 2.5.2 或完整重汇编 Android 17 bootclasspath DEX，破坏 hiddenapi 标志、方法布局或漏掉 API。开机时出现 `NoSuchMethodError`、`DataLoaderService` 等 system_server/zygote 错误，手机甚至没有进入第二次震动。

解决：回到已知可开机原始 jar，仅做等长指令 patch；每次都做方法 API 全量 diff、ZIP 测试和实机 boot_completed 验证。

### 6.2 认为“能解包/能挂载”就等于镜像可启动

EROFs 镜像还依赖 UUID、label、SELinux xattr、目录标签、AVB hashtree footer、原分区尺寸和 super 固定布局。缺任一项都可能早期启动失败。

解决：`mkfs.erofs` 后恢复 UUID/label/xattr；用 `avbtool add_hashtree_footer --algorithm NONE` 保持原尺寸；`fsck.erofs`、`avbtool verify_image`、重新从 super 固定偏移抽出并 `cmp`。

### 6.3 super 组装和刷写脚本问题

- PowerShell 中文脚本曾因编码损坏出现乱码、引号未闭合和 `Unexpected token`。
- `fastboot getvar` 输出在 stderr，PowerShell `$ErrorActionPreference=Stop` 会把正常输出当 `NativeCommandError`。
- 某些刷机工具占用 fastboot 进程，脚本误判或无法读 product。
- WSL 直接复制 13GB super 曾报 `Cannot allocate memory`。

解决：脚本使用 UTF-8 BOM/纯 ASCII 关键逻辑；用 `ProcessStartInfo` 合并 stdout/stderr 并按退出码判断；检测 fastbootd 的 `is-userspace: yes`；大文件用 Windows 原生复制，再由 WSL `dd` 固定偏移写入并回读校验。

### 6.4 只改 init rc 权限但忽略 SELinux

Stage14 写了 `chmod 0666`，文件内容也确实进了 `/system/etc/init/k90-native.rc`，但内核 audit 明确拒绝 `init setattr proc_powerhal_cpu_ctrl`，所以重启后不生效。看到脚本存在不能宣称修复。

### 6.5 充电状态错误地归因于图标资源

真实根因是附加电池广播 `notifycode=-1`。ColorOS 位运算把 -1 解释成所有错误位，从而 `batteryCharging=false`。手工广播 `notifycode=0` 后 SystemUI 立即变为 charging=true，证明确认无误。

### 6.6 直接改 SystemUI APK 的风险

SystemUI 是 platform 签名的持久系统应用。直接 apktool 重编、重签会破坏签名权限和共享 UID；运行时塞 RRO 又会被 idmap2 拒绝。优先改上游 framework/service 输入，或使用原签名/预置 overlay。

### 6.7 电源键 EVIOCGRAB 的副作用

抢占 event0 虽能绕过慢路径，但音量键也在同一设备上，造成音量、长按电源、截屏组合键失效。该路线只能作为探针，不应作为最终系统修复。

### 6.8 vendor/odm 身份被 OnePlus 覆盖导致无信号

`libxiaomi_modem_api.so` 读取 `ro.product.odm.name/device` 上报基带选择 NV。错误 PMB110 身份会导致 `SYS_NV_SIG_ERR_IND`、IMEI check fail、双卡 POWER_OFF。应用层身份与底层身份必须分开。

### 6.9 NFC 路由试验的坑

只改 Java hook 无法解决 native ESE discovery；直接把 route 改 DH 可能令 HAL AIDL open code 1 循环。不要在系统运行中手动 stop/start NFC HAL，必须完整重启验证。

## 9. 保数据刷写与不开机诊断

刷写前：

1. 确认设备是 `prague`、Bootloader 已解锁。
2. 关闭所有占用 fastboot 的第三方刷机工具。
3. 进入 fastbootd，确认 `fastboot getvar is-userspace` 返回 yes。
4. 只刷 super，不执行 `-w`，不 erase userdata/metadata。

命令：

```powershell
fastboot devices
fastboot getvar product
fastboot getvar is-userspace
fastboot flash super images\super.img
fastboot reboot
```

不开机时不要立刻清数据或刷官方包：

- 若能进 recovery/adb：抓 `logcat -b all`、`dmesg`、`pstore/console-ramoops`。
- 若只有 fastboot/fastbootd：先记录 slot、is-userspace、分区布局；把当前 system 从 super 抽出做 hash 比较。
- 没有第二次震动通常是 zygote/system_server 或 early mount/AVB 失败，不是 userdata。
- 使用已知可开机的 Stage13C system 替换 super 中 system 区即可保数据回退。

## 10. 实机验证清单

每次新镜像至少验证：

1. `sys.boot_completed=1`，连续重启两次。
2. 电话、移动数据、短信、双 SIM（如有）、飞行模式。
3. 状态栏真实信号、插拔充电、拔线后图标/颜色恢复。
4. `dumpsys battery` 与附加电池广播字段。
5. 指纹录入、锁屏图标、解锁；人脸删除后重新录入。
6. 电源键短按、长按、音量键、截屏组合键。
7. 相机拍照、录像、第三方调用与保存返回。
8. AOD 持续时间、双击亮屏、误触保护。
9. CPU 节点权限和 10 秒 PowerHAL 错误计数。
10. `logcat` 中 system_server/SystemUI/vendor HAL 崩溃循环和每分钟重复错误。

## 11. 迁移到新电脑后恢复环境

1. 安装/启用 WSL2 和虚拟机平台。
2. 安装 Ubuntu 24.04，按 `06_WSL关键产物_虚拟磁盘不迁移\环境清单` 恢复软件包。
3. 把该目录中的工具 JAR、最终 JAR、smali 源码和 system 镜像放入新的工作路径。
4. 安装 Android platform-tools 驱动并确认 adb/fastboot。
5. 运行目录清单和 SHA-256 校验。
6. 全局搜索旧绝对路径 `C:\Users\USERNAME`、`D:\K90_`、`/mnt/c/Users/USERNAME`、`/mnt/d/K90_` 并更新为迁移根目录。

## 12. 安全边界

- 不复制或伪造 TEE/RPMB/StrongBox 私钥。
- 不绕过付费内核授权或移除第三方内核验证。
- 不全局关闭 SELinux；只加最小规则。
- 不通过假属性宣称硬件不存在的 1Hz LTPO、长焦、ESE 或 VOOC。
- 不随意替换 modem、preloader、lk、nvdata、nvcfg、persist、protect。
- 每项修复都要有日志、回读和重启验证，不能把“编译成功”写成“修复成功”。
