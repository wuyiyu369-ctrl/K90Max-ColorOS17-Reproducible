# K90 Max 小米底层与 ColorOS 17 功能可迁移审计

> 第一版实机 + 底包静态审计，2026-11-02。
> 原则：先确认真实硬件/HAL 能力，再让 ColorOS 通过内置适配层访问；不用 Root 模块，不伪造硬件状态。

## 总结

K90 Max 的大部分 Xiaomi/MTK/Novatek 底层服务仍在 ColorOS 移植系统中运行。主要矛盾不是硬件消失，而是 ColorOS 只认 OPLUS 私有接口。建议保留 ColorOS UI，增加少量可审计的内置协议适配服务，不整体移植小米 SystemUI 或设置应用。

| 功能 | 小米底层证据 | ColorOS 当前问题 | 可迁移性 | 建议 |
|---|---|---|---|---|
| 充电协议/双闪电 | `IMiCharge` 与 PD/PPS/QC/私有快充节点都在 | OPLUS `ICharger` 缺失 | 高 | P0 |
| 色彩/护眼 | Xiaomi `IDisplayFeature`、`IMiHwcExtension`、MTK PQ 在运行 | ColorOS 枚举与 HWC 不匹配 | 高 | P0 |

## 显示链路

### 色彩切换

实机已注册：

- `vendor.xiaomi.hardware.displayfeature_aidl.IDisplayFeature/default`
- `vendor.xiaomi.hardware.display.mihwcextension.IMiHwcExtension/default`
- `vendor.mediatek.hardware.pq_aidl.IPictureQuality_AIDL/default`

SurfaceFlinger 只公布标准色彩模式 `0, 7, 9`，但 ColorOS 写入 `display_color_mode=301`。本次启动日志中大量出现 `map unknown ... to default color mode`，说明色彩切换实际回落到默认模式。

可行方案：内置 ColorOS 色彩枚举到 Xiaomi DisplayFeature/MTK PQ 的映射，并保留 HDR 和色域自动切换。

### 最低亮度

- 背光设备：`/sys/class/leds/lcd-backlight`。
- 硬件 `max_brightness=16383`。
- ColorOS 框架当前 `mScreenBrightnessRangeMinimum=222`。
- 当前亮度映射约为 `2~490 nit`，`EvenDimmerBrightnessData=null`。

结论：低亮度问题主要是 ColorOS 显示配置和亮度 LUT 没对上原面板。应从小米原系统提取该面板低亮段曲线并转成 ColorOS/AOSP 可消费的 DisplayDeviceConfig；如低亮还依赖 DC/PWM，再映射到 Xiaomi DisplayFeature。

### 1K/1.5K

- 当前 `wm size` 与物理显示都是 `1280x2772`。
- 60/120/144/165 Hz 四个 HWC mode 全部为 `1280x2772`。
- 当前没有第二组物理分辨率 mode，因此所谓 1K 切换至少没有通过标准 HWC mode 生效。

还需逆向 `IMiHwcExtension/IDisplayFeature` 是否提供面板 scaler 或 MML 渲染分辨率切换。若面板只有单一 timing，只能做真实的 HWC/GPU 渲染分辨率缩放，不能宣称物理分辨率切换。

### 护眼

ColorOS EyeProtect 已在计算 RGB/CCT，但日志有 `setDispParam fail value:20` 并回落到 HIDL MiscService。说明算法和 UI 在，失败点是底层写入接口。应把 ColorOS 的 CCT、饱和度和昼夜策略映射到 Xiaomi DisplayFeature/MTK PQ。

## 注视熄屏与 AON

Android AttentionManager 已解析到 `com.aiunit.aon/.AONAttentionService`。实测 `checkAttention` 可派发，服务能打开前摄；但模型后端报 `mAIBoostHandle=0`、`getInputNum=-1`、`getOutputNum=-1`，最终 `FusionWithEyeRuntime init error`。

结论：开关与 Attention 协议已接通，坏在 OPLUS AON 模型没有连上 Xiaomi/MTK APU 推理后端。需核对模型文件、APU 运行库、文件路径和 SELinux。

## 充电协议与图标

原机实际节点提供：

- 标准 SDP/CDP/DCP：`real_type/type`。
- QC：`qc3_type`、`quick_charge_type`。
- PD/PPS：`pd_type`、`pd_authentication`、`pd_verify_done`、`apdo_max`。
- 小米私有快充：`adapter_id`、`power_max`、`fastcharge_mode` 与 MiCharge HAL。
- 充电泵：`cp_master` 及 MTK HV divider charger。

当前连接电脑时实测为 `SDP / quick_charge_type=0 / fastcharge_mode=0 / power_max=0`，不应显示快充。

映射原则：

1. 双闪电只绑定小米私有快充的明确证据。
2. PD/PPS/QC 保留各自快充语义，不因功率大于 20W 就误报 SVOOC/双闪电。
3. SDP/CDP/DCP 只显示单闪电；断开、省电和温控限速时必须清理或降档。
4. UFCS 目前只有 OPLUS 参考文件，暂无 K90 小米底包硬件支持证据，暂不伪报。
5. 需用原装小米快充、PD/PPS、QC 充电器各采样一次，锁定私有枚举真实值。

## CPU、GPU 与独显增强

实机正在运行：

- `vendor.mediatek.hardware.gpuserv.IGpuService/default`
- `vendor.xiaomi.hardware.framemaster.IFrameMaster/default`
- `vendor.xiaomi.hardware.framecapturemanager.IFrameCaptureManager/default`
- `vendor.novatek.hardware.visdisplaysrv.IVisdisplaysrv/default`
- `vendor.xiaomi.hardware.postprocservice.IPostProcService/default`
- `vendor.xiaomi.hardware.videoservice.IVideoService/default`
- MTK MML/PQ/APU/Neuron 服务
- Xiaomi MiPower/Uniperf 与 MTK Power HAL

结论：原机独显、插帧、超分、游戏增强的底层能力没有丢，但 ColorOS GPA/OStats 调用的是 OPLUS GPU 代理和节点。适合做策略请求翻译层，不应锁频、关温控或伪造档位。

## Bose、MiSound 与 Dolby

底包存在：

- `persist.vendor.audio.fpsop.game.effect.bose=true`
- `libmisoundfpsop.so`、MiSound AIDL/DSP parser/SA 库
- Dolby DMS/DVS、Dolby Vision 与 DAX 配置

同时底包设置 `persist.vendor.audio.misound.disable=true`，说明当前系统刻意关闭了 MiSound 主效果链。

建议保留 ColorOS 音效中心 UI，增加 MiSound/Bose 参数后端适配，并避免 Dolby 与 MiSound 在同一音频 session 重复处理。不能只把 disable 改成 false，否则有无声、爆音或 AudioFlinger 重启风险。

## 虚拟运行内存

实机当前：

- 物理内存约 15.6 GB。
- `/dev/block/zram0` 已启用，约 17.1 GiB，LZ4 压缩，已使用约 3.0 GiB。
- Xiaomi `vendor.xiaomi.hardware.swap.ISwap/default` 正在运行。
- ColorOS 为 `persist.sys.oplus.nandswap=false`、`err=1008`、`swapsize.curr=0`。
- Athena 重复读取不存在的 OPLUS 专用节点 `/sys/block/zram0/hybridswap_meminfo`。

结论：zRAM 已有效；失效的是 ColorOS NAND 冷页交换。首选让 ColorOS UI 适配 Xiaomi Swap HAL；次选只显示真实 zRAM 状态并隐藏不兼容的 NandSwap 容量开关。不能只强制属性为 true，因为完整 NandSwap 还依赖内核 procfs、线程和 swap 优先级路由。

## 密钥、TEE 与 OPLUS CryptoEng

实机已注册 Android KeyMint/StrongBox、远程预置组件，以及 Xiaomi MiKeyBag、Soter、FIDO、MiSharedAuth、Mlipay、MiCertificate/MRM、OTrPAgent。

ColorOS 日志明确报：`getService fail.vendor.oplus.hardware.cryptoeng.ICryptoeng/default`。

可行边界：

- 可实现内置 OPLUS CryptoEng 兼容服务，映射到 Android KeyMint 或 Xiaomi 已有安全服务，让 ColorOS 调用本机 TEE。
- 不能复制、导出或伪造另一台 OPPO 设备的 TEE 私钥和证明链。
- 当前还有远程密钥预置用户同意未授予、个别应用 attestation challenge 过长等独立问题，不能全部归因于 CryptoEng。

## 建议实施分组

### A 组：低风险，优先

- ODM 预编译 SELinux：PowerHAL `perfserv_freq`、指纹属性读取。
- 清理错误 DSDA/双 NR 声明，恢复合并信号正确数据源。
- 充电适配先完成不误报的协议分类。
- 色彩枚举和最低亮度配置对齐。

### B 组：中风险，独立验证

- Xiaomi DisplayFeature 对接 ColorOS EyeProtect/色彩。
- Xiaomi Swap HAL 对接 ColorOS 内存拓展 UI。
- MiSound/Bose 对接 ColorOS 音效中心。
- AON 模型/APU 后端修复。
- FrameMaster/Novatek 对接 ColorOS 游戏策略。

### C 组：高风险，必须单独候选镜像

- 真实 1K/1.5K scaler/mode 切换。
- OPLUS CryptoEng 协议兼容服务。
- 修改 Audio HAL 效果链、HWC mode 列表或 TEE 调用。

## 明确不做

- 不把快充功率大小直接当成小米私有快充。
- 不锁 CPU/GPU 频率，不关闭温控。
- 不仅靠 DPI 伪装 1K/1.5K。
- 不用假属性宣称 NandSwap、UFCS、双 NR 已支持。
- 不复制、导出或伪造硬件 TEE 私钥。
- 不再以 KernelSU/LSPosed 模块作为最终修复。

| 传感器增强 | 标准 Sensors HAL 和 ColorOS Java SensorService 存在；OPLUS SensorFeature 私有接口缺失 | MTK Sensors、Xiaomi CIT SensorService | 距离/陀螺仪等基础能力可用；口袋模式、抬手亮屏、AOD 场景、部分姿态策略需逐项验证，P1/P2 |

### 补充优先顺序

1. 先处理 `IPerformance/URCC/Touch/DisplayPanelFeature` 四条主链，它们与当前性能差、游戏增强、亮度和护眼问题直接相关。
2. 充电、BatteryAntiAging、信号和网络协同使用真实小米状态源，避免每个界面各做一套临时判断。
3. 再验证相机稳帧、NFC 钱包、传感器场景、Wi-Fi 增强和 DRM；这些不能仅凭服务缺失就判定基础功能损坏。
4. OStats、工程服务和工厂服务最后处理，只补实际调用到且有明确小米等价能力的接口。
